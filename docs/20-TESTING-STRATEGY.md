# 20 — Testing strategy

Decision status: see the [README decisions table](../README.md#decisions).

## Purpose and evidence standard

Define executed verification for [requirements](01-PRODUCT-REQUIREMENTS.md) and [acceptance gates](22-ACCEPTANCE-CRITERIA.md). The test tooling baseline uses pytest and, when async components are implemented, an async test plugin, HTTPX mock transport, fake Discord/CLI transports, real temporary SQLite databases, controllable clocks and subprocess fixtures. Phase 1 uses pinned pytest 9.2.0 and synchronous tests on Windows/CPython 3.14.6. Its executed results are recorded in doc 22; later-feature tests below remain required before those features can be accepted.

Unit tests verify pure rules. Integration tests exercise services with real SQLite and controlled external boundaries. Live tests are opt-in, explicitly configured, bounded and separated from ordinary CI/local checks. Mocks cannot establish actual Discord permissions or subscription allowance compatibility. Test failures are reported with scope and blocker, never converted into assumed success.

Use independent expected values and behavior assertions rather than tests mirroring code structure. Concurrency tests use separate SQLite connections and barriers, not sequential mocks. Subprocess tests spawn a harmless local fixture and its child to prove timeout/process-tree cleanup on the deployment OS. Network tests instrument actual resolver/transport destination selection. Live URLs are never used by ordinary tests.

## Live integration gates

| ID | Environment and procedure | Evidence and gate |
|---|---|---|
| L01 Discord | Owner-created sandbox guild, dedicated bot, test operators; setup twice, wrong-channel commands, roles, permission loss, delete/rename resources, controls after restart, long-job defer | Sanitized guild/resource/message IDs, timing and screenshots/logs; no duplicates; private errors; actual permission overwrites and component/message limits verified |
| L02 Provider | Per candidate/version/account/model; follow full [10](10-AI-PROVIDER-INTEGRATION.md) procedure using permitted real mechanisms | Version/hash/billing/auth/allowance windows and freshness, actual capacity visibility, sufficient/exhausted/unverifiable behavior, safe task/cancellation and before/after evidence. Missing critical real evidence = BLOCKED, even if T08 passes |
| L03 Discovery/research | Review current selected source terms/licensing/access policy; make a small allowed query and official-site fetch within approved rate; test attribution and TLS/network restrictions | Policy URL/date/version, bounded request/result, provenance/attribution, source parser compatibility; no volume/abuse stress tests on public infrastructure |
| L04 Recovery | Locally run disposable end-to-end data, interrupt process, backup/restore to different root, restart and inspect | No AI/hunt resumed; all identity/credit/evidence links consistent; prior partial summary and manual recovery work |

If production account exhaustion cannot ethically/practically be tested, do not deliberately consume a subscription to force it; document the gap and seek an approved permitted verification method. Until the required proof exists, autonomous provider eligibility stays blocked. No real unsolicited outreach test is permitted or necessary.

## Execution and reporting

Future standard commands (only once implemented): `python -m pytest tests/unit tests/integration`; opt-in live suite with explicit `--run-live` plugin option implemented to default skip. Live tests require separate sandbox variables and never reuse ordinary tests' accidental environment. Clean temporary data, not real registry records. Record commit/artifact version, Python/dependency versions, OS, timestamp, executed command, passed/failed/skipped totals, test IDs, sanitized evidence paths and unresolved gaps. A skipped test is not passed. Trace every phase to [22](22-ACCEPTANCE-CRITERIA.md); no arbitrary coverage percentage replaces these critical behavioral gates.

## MVP and post-MVP test sequencing

The non-AI MVP runs the applicable T01–T06, T10, non-AI T11 and T12/T14/T16–T18 cases, plus T03/T13 scheduler/cancellation/restart cases without AI, L01 for its Discord paths, L03 for permitted discovery and safe website research, and L04 for basic verified-copy recovery. Disabled AI actions are tested for visible fail-closed errors and zero CLI execution. L02 findings are recorded during Phase 0, but a BLOCKED provider does not block the owner-authorized non-AI release. T07–T09, AI-specific T11, T15 and AI-specific live paths remain required before their later features are released. The non-AI `/research` path must pass while provider detection/authentication/allowance/execute spies all observe zero calls; analyze:true must be denied before enqueueing in the MVP. Evidence must remain usable if a later optional analysis fails. Phase 4a is mandatory for the MVP even when L02 is BLOCKED.

Marker-based publication reconciliation and the UNCERTAIN delivery tests are post-MVP; the MVP must already test the safer manual-inspection hold. Expanded backup-manifest tests are post-MVP; basic verified-copy and restore tests are not deferred. The future MCP interface is post-MVP and requires explicit extension authorization; disabled-MCP isolation checks remain mandatory. Record scoped pass/fail/skip results separately so a non-AI release cannot be mistaken for full autonomous acceptance.

## Phase 2 verification boundary

Automated tests exercise the native discord.py command tree and persistent views, fake interactions and REST transport, and real SQLite setup journals. They cover command restrictions, preview confirmation, repeat setup, concurrent claims, partial failures, uncertain resource/publication holds, permission loss, restart routing and disabled workflows. These tests do not establish actual Discord permissions, delivery or rate-limit behavior. L01 remains a separate live gate; no opt-in live pytest plugin is implemented yet.

## Research recovery verification increment

T13/T16 now include research-specific backup/restore tests: retain full evidence rows and hashes, restore unfinished jobs/runs as INTERRUPTED, reject valid-FK but wrong-business/job/hash evidence, and verify that temporary WAL sidecars do not prevent normal private-root startup. A disposable child-process abrupt-exit drill separately exercises actual initialize/recovery against copied live-source test evidence. Read-only scripts/check_research_prerequisites.py checks migration ledger/version, SQLite/FK/research integrity, setup state and local research counts; it never proves site permission or live Discord acceptance and always reports full_phase4a_accepted:false.

## Isolated T12 core increment

The D16-authorized offline CRM tests enumerate all 64 stage pairs against an independently encoded contract, check prerequisite failures/rollback, stale revisions, same-business public evidence/hash/time validation, unique manual qualification with a two-connection race, immutable note corrections and stage/history persistence through backup/restore. Service tests inject fresh authorization and independently check persisted channel/readiness/role policy and explicit confirmation, with network/provider spies and no Discord registration. This validates the isolated core, not full T12/P6 acceptance: contact capture, real Discord confirmation/rendering, manual drafts, reminders, exports and live acceptance remain pending.
